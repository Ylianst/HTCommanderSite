# How internationalization (i18n) works on the HTCommander site

This site is a plain static site hosted on **GitHub Pages** at
`https://ylianst.github.io/HTCommanderSite/`. It is available in **9 languages**
(English plus 8 translations) served from per-language subfolders:

```
/index.html          ← English (source of truth)
/es/index.html       ← Spanish
/ja/features/aprs.html
...
```

There is **no runtime translation and no framework**. Every localized page is a
real, pre-rendered `.html` file produced by a small Node script from the English
pages plus JSON string catalogs. This keeps the site fast, cache-friendly and
fully functional with JavaScript disabled.

> **Golden rule:** the English `.html` files are the single source of truth for
> *content and layout*. Never hand-edit the files under `de/`, `es/`, `fr/`,
> `hi/`, `it/`, `ja/`, `pl/`, `zh/` — they are generated and will be overwritten.
> Edit English + the catalogs, then rebuild.

---

## 1. Files involved

| Path | Role |
| --- | --- |
| `tools/build-i18n.js` | The generator. No dependencies. |
| `i18n/config.json` | Language list, base URL, and the list of pages to generate. |
| `i18n/common.json` | Shared strings (nav, footer, common buttons/eyebrows). Merged into every page. |
| `i18n/pages/<page>.json` | Per-page string catalog. See naming below. |
| `assets/js/i18n.js` | Runtime **language switcher** + the generated `TRANSLATED` manifest. |
| `assets/css/style.css` | Contains the `.nav__lang` / `.lang__*` switcher styles. |
| `<lang>/**` | **Generated output** — do not edit by hand. |

### Catalog file naming
A page's catalog lives at `i18n/pages/` with `/` replaced by `__`:

- `downloads.html` → `i18n/pages/downloads.html.json`
- `features/aprs.html` → `i18n/pages/features__aprs.html.json`

---

## 2. Building

From the site root:

```powershell
node tools/build-i18n.js
```

This is idempotent and safe to run any time. It:

1. **Wires** each English page (adds the language-switcher container, `hreflang`
   alternates, the `HT_PAGE` config and the `i18n.js` include) and writes it back
   in place.
2. Emits `<lang>/<page>` for every non-English language.
3. Rebuilds the `TRANSLATED` manifest inside `assets/js/i18n.js`.

Output ends with e.g. `Done. 232 localized files written; manifest updated.`

## 3. How a catalog works

A catalog maps an **exact English source string** to its translation in each
language:

```json
{
  "Download the app": {
    "de": "App herunterladen",
    "es": "Descargar la app",
    "fr": "Télécharger l'app",
    "hi": "ऐप डाउनलोड करें",
    "it": "Scarica l'app",
    "ja": "アプリをダウンロード",
    "pl": "Pobierz aplikację",
    "zh": "下载应用"
  }
}
```

At build time the generator merges `common.json` with the page catalog
(`Object.assign({}, common, pageCatalog)` — the page can override a common key),
then does a **literal, collision-safe substitution** of every English key with
its translation for the target language.

- Keys must match the English HTML **exactly**, including inline tags and HTML
  entities. For example the key must be `Audio &amp; SSTV` (not `Audio & SSTV`)
  if the source markup uses `&amp;`.
- A key may include inline markup, e.g.
  `Command your <span class="text-gradient">handheld radio</span> from anywhere.`
  — the translation keeps the same tags with translated inner text.
- Strings **not** present in any catalog are left in English.

### Two-pass, collision-safe replacement
`translate()` sorts keys **longest-first**, swaps each match for a private
placeholder token, then swaps tokens for translations. This guarantees a short
key can never corrupt a longer already-translated fragment (e.g. keying
`Map` will not damage a sentence containing `OpenStreetMap` if that sentence is
also a key).

## 4. Path handling (why the output "just works" in subfolders)

English root pages use `assets/...`; a page in `/es/` needs `../assets/...`, and
a page in `/es/features/` needs `../../assets/...`. The generator fixes this
automatically per page depth.

- `rewritePaths()` rewrites relative `src`/`srcset`/`href`/`content` values by
  the correct number of `../` for the page depth (including `data-src` /
  `data-srcset`, and every candidate URL in a `srcset` list).
- **Absolute** URLs, `mailto:`/`tel:`/`data:` and in-page `#anchors` are left
  untouched.
- **Cross-links auto-upgrade:** if a link points to another page that *is*
  translated (listed in `config.pages`), the relative link is left as-is so it
  resolves **in-language** (e.g. `es/index.html`'s `downloads.html` →
  `/es/downloads.html`). If the target is **not** translated yet, the link is
  rewritten with `../` to fall back to the English copy. Add the target to
  `config.pages`, rebuild, and the link upgrades to in-language automatically.
- `rewriteJsonAssets()` handles asset paths inside inline
  `<script type="application/json">` data blocks (used by the feature gallery),
  which `rewritePaths` intentionally skips.

## 5. What is deliberately NOT translated (the "shield")

Before translating, the generator **shields** these from substitution so a
translatable word can never corrupt them:

- `src="..."`, `srcset="..."`, `sizes="..."` and `href="..."` — filenames,
  responsive image lists and links.
- `alt="..."` — image alt text. **Alt text therefore stays English** across the
  whole site (a deliberate, consistent trade-off; alt is non-visible).
- `"img": "..."` values inside JSON data blocks.

By convention (just by **not** adding them to a catalog) we also keep these in
English for accuracy and consistency:

- **Product/brand names & acronyms:** APRS, AX.25, KISS, CTCSS, SSTV, Winlink,
  EchoLink, Bluetooth, Android Auto, dump1090, MQTT, RepeaterBook.com, etc.
- **UI labels shown verbatim in the app**, usually wrapped in `<strong>` in the
  copy, e.g. `<strong>Connect</strong>`, `<strong>Settings</strong>`,
  `File → Settings`, `<strong>Activate</strong>`, `GPS Lock`.
- **Code/hex/protocol reference** (`<code>0x01</code>`, byte-decode `<pre>`
  blocks, the BSS "Known data types" table).
- **`<meta name="description">` and `og:*` descriptions** (long SEO text).
  Note the page `<title>` **is** translated where a catalog entry exists.

## 6. The `data-captions` carousel — apostrophe gotcha

The home page hero has a rotating caption carousel. The captions live in a
**single-quoted** HTML attribute holding a JSON array:

```html
<p ... data-captions='["First caption", "Second caption", ...]'>First caption</p>
```

Because the attribute is single-quoted, a raw apostrophe (`'`) inside a
translation would terminate the attribute and break `JSON.parse` in
`assets/js/main.js` (the carousel would silently show nothing). **Escape
apostrophes as `&#39;`** in caption translations, e.g.:

```json
"Built-in address book for your contacts": { "fr": "Carnet d&#39;adresses intégré pour vos contacts" }
```

`&#39;` is not a `'`, so it does not close the attribute; the browser decodes it
back to `'` before `main.js` reads and parses it. (Only the caption strings need
this — normal element text can use a literal apostrophe.)

## 7. Runtime: the language switcher

`assets/js/i18n.js` renders the globe/language dropdown into the
`<div id="langSwitch">` container. It relies on two things the generator writes:

- A per-page config injected before `</body>`:
  `window.HT_PAGE = { lang: "es", page: "features/aprs.html", root: "../../" };`
- The generated `TRANSLATED` manifest (between the `BUILD:TRANSLATED-START/END`
  markers) listing which pages exist in which languages.

When you pick a language it navigates to the same page in that language
(`root + code + "/" + page`), or falls back to that language's home page if the
current page isn't translated there. `hreflang` alternates in each page `<head>`
give search engines the same information.

## 8. Common tasks

### Add / change a translation on an existing page
1. Edit the page's catalog in `i18n/pages/` (or `i18n/common.json` for shared
   nav/footer strings).
2. `node tools/build-i18n.js`.

### Translate a brand-new page
1. Author the English page normally (relative `assets/...` and `page.html`
   links, `<html lang="en">`).
2. Create `i18n/pages/<page-with-__>.json` with the page's strings ×8 languages.
   (Nav/footer come from `common.json` automatically.)
3. Add the page path to `pages` in `i18n/config.json`.
4. `node tools/build-i18n.js`. Cross-links from other pages to it upgrade to
   in-language on the next build.

### Add a new language
1. Add `{ "code": "xx", "label": "XX", "name": "Native name" }` to `languages`
   in `i18n/config.json`.
2. Add the `"xx"` translation to **every** catalog (`common.json` and each file
   in `i18n/pages/`). Missing keys simply fall back to English.
3. Add the language to the `LANGS` list in `assets/js/i18n.js` so it appears in
   the switcher.
4. `node tools/build-i18n.js`.

---

## 9. Hosting notes

- Project page base path is `/HTCommanderSite/` with **no** custom domain, so all
  internal links are **relative** — never root-absolute (`/assets/...`).
- `.nojekyll` is present so GitHub Pages serves the folders as-is.
- Re-run the build and commit the regenerated `<lang>/` folders + updated
  `assets/js/i18n.js` whenever English content or catalogs change.
